## เป้าหมายการตรวจรับ

ตรวจว่าผู้ใช้สามารถบันทึกค่าใช้จ่ายที่จ่ายแยกจากเงินรับสุทธิ เห็นผลต่อเงินเหลือ แก้กลับรายการโดยไม่ลบประวัติ และใช้งานตามสิทธิ์ของแต่ละบทบาทได้ โดยข้อมูลของแต่ละบริษัทต้องไม่รั่วข้ามกัน

## หลักฐานตัวเลข

รายการ `UAT-AD-1789613633` ถูกบันทึกเป็นค่าโฆษณาส่วนกลาง 12,345 สตางค์ และมีรายการแก้กลับที่อ้างถึงต้นฉบับในจำนวนเท่ากัน รายการ `UAT-FINANCE-1789613633` ถูกบันทึกโดยบทบาทฝ่ายการเงินเป็นค่าเดินทาง 1,000 สตางค์ และมีรายการแก้กลับในจำนวนเท่ากัน

หลังจบ UAT:

- ค่าใช้จ่ายที่ยังมีผลของร้าน TikTok เท่ากับ **0.00 บาท**
- เงินเหลือหลังค่าใช้จ่ายที่บันทึกกลับเป็น **9,440.00 บาท**
- บทบาทของ `staff@chino.demo` ถูกคืนเป็น **ปฏิบัติการ** และเปิดหน้าค่าใช้จ่ายไม่ได้ตามสิทธิ์เดิม
- หน้าประวัติการทำงานแสดงเหตุการณ์ **บันทึกค่าใช้จ่ายร้าน**, **แก้กลับค่าใช้จ่ายร้าน** และ **เปลี่ยนสิทธิ์สมาชิก**
- ไม่พบ browser error ใน session ของเจ้าของ ผู้ตรวจสอบ การตลาด และพนักงาน

## การตรวจระดับระบบ

ตรวจเส้นทางครบจากหน้าจอ → API → PostgreSQL → การคำนวณหน้าเงินรับและต้นทุน ฐานข้อมูลยืนยันว่ารายการ UAT ทั้งสองชุดมีต้นฉบับและรายการแก้กลับครบ 4 แถว และยอดสุทธิที่ยังมีผลเป็นศูนย์ การแก้กลับจึงรักษาประวัติโดยไม่ทิ้งผลกระทบต่อยอดปัจจุบัน

ชุดตรวจอัตโนมัติของ PR ผ่าน **59 integration tests** และ **18 browser tests** ครอบคลุม replay, concurrent request, tenant/RLS isolation, append-only grants, สูตรเงินเหลือ และ flow มือถือ

ระหว่าง UAT เครื่องมือควบคุมเบราว์เซอร์ไม่สามารถกดปุ่ม submit ผ่าน accessibility reference บางรายการได้ จึงใช้ DOM click ใน session เดิมเพื่อเดิน flow ต่อ พฤติกรรมปุ่มจริงผ่าน Playwright browser tests และไม่พบข้อผิดพลาดของแอป จึงจัดเป็นข้อจำกัดของเครื่องมือทดสอบ ไม่ใช่ product defect
